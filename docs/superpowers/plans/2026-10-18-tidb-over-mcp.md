# Plan: TiDB over MCP, read-only snapshot reads (v0.8.11)

Slice B of `/Users/rudy/.claude/plans/system-instruction-you-are-working-ethereal-stream.md` (finish roadmap P1).

## Context

TiDB can't be shared with agents today. Its `START TRANSACTION READ ONLY` is rejected, or becomes a no-op when `tidb_enable_noop_functions` is on, so TableIQ has no read-only transaction to wrap agent reads in (`docs/ENGINES.md`, "TiDB over MCP: still closed"). TiDB does have a stale-read transaction, `START TRANSACTION READ ONLY AS OF TIMESTAMP NOW(6)`. It refuses DML ("only support read-only statement during read-only staleness transactions"), but it reads a snapshot, and DDL and `SET GLOBAL` run through it (proven in `tests/mcp_live.rs` `tidb_has_no_default_read_only_transaction`).

**User decision (2026-10-17):** open TiDB to agents for reads only, using snapshot reads. Writes stay refused even if the user ticks "Allow writes".

## Approach (mirrors how CockroachDB was opened in v0.8.4)

### 1. Profile (`src/lib/profiles.json`, read by both Rust and TS)
- `tidb`: `"agent": true`, `"agentSince": 4`, and a new `"agentReadOnly": true`.
- Remove `agentNote` from TiDB, and remove the `agentNote`/`agent_note` field and its branch from Rust and TS: no other profile sets it, so it would be dead and untested, and `AGENT_NOTE` already explains every closed product. Add an `agentReadNote`, short and shared by the Settings row and agents: "Read-only. Agents read a snapshot taken when each query starts; writes are never allowed." The longer explanation (node clock and cluster freshness, why DDL is not refused by TiDB, tested on TiDB 8.5) lives in `docs/ENGINES.md#tidb-over-mcp`.
- Rust `Profile` (`src-tauri/src/profiles.rs`:12) gets `#[serde(default, rename = "agentReadOnly")] pub agent_read_only: bool` and `#[serde(default, rename = "agentReadNote")] pub agent_read_note: Option<String>`. The TS `Profile` interface gets the same two fields.
- Text that names TiDB as closed or the reviewed set changes: `AGENT_NOTE` (Rust and its TS mirror) adds TiDB; `reconfirm_block` for a product with `agent_read_only` reads: "TiDB was shared before TableIQ supported it over MCP. Untick and tick it in Settings → MCP to share it again (it stays read-only)."; `docs/ENGINES.md` "TiDB over MCP: still closed" becomes `#tidb-over-mcp` with these sub-headings: what agents can do; snapshot semantics and the cluster freshness caveat; writes never allowed, and why; what is refused (families and alternatives); recommended read-only role (the SQL in §7); tested versions (8.5) and what is untested (TiDB Cloud); the probes; the known limit that a TiDB saved as plain MySQL is refused with the MySQL text before its first connect; the 30s agent timeout's `KILL QUERY` needs `enable-global-kill` (on by default since TiDB 6.1) when agents reach TiDB through a load balancer (Eng L5); the comments on `tidb_has_no_default_read_only_transaction` and the `server.rs` tool-description test move with it.
- `agent_rev()` becomes 4, and `AGENT_REV` (TS) follows `agentSince`. An allowlist entry made before 4 is refused until the user re-shares (`reconfirm_block`). That is the existing mechanism.

### 2. Guard dialect (`src-tauri/src/mcp/guard.rs`)
- `pub const TIDB: &str = "tidb"`; `base_engine` maps `tidb` to `mysql` (like `COCKROACHDB` to `postgres`).
- `read_only_wrap("tidb", sql)` gives `["START TRANSACTION READ ONLY AS OF TIMESTAMP NOW(6)", sql, "ROLLBACK"]`.
- The read-only rules already refuse every DDL (write words plus the `READ_FIRST` whitelist), `SET` (incl. `SET GLOBAL`, `SET @@tidb_snapshot`), `ADMIN`, `PLAN REPLAYER`, `TRACE`, `BATCH`, `SPLIT`, `FLASHBACK`, `RECOVER` and `RENAME` (first keyword not in `READ_FIRST`), and `IMPORT INTO` (`INTO`). Every one of these gets a `guard_suite` row.
- New `scan()` rule on the MySQL base (so on MySQL, MariaDB and TiDB): a TiDB executable comment `/*T!` is refused like `/*!` and `/*M!`. The 2026-10-18 probe showed TiDB runs its body (`SELECT 1 /*T![clustered_index] , 2 */` returned two columns), so a statement could hide inside one.
- New read-only rule on the MySQL base: `NEXT VALUE FOR` (and `NEXTVAL`/`SETVAL`/`LASTVAL`) is refused when writes are off, which on TiDB is always. The probe showed `SELECT NEXT VALUE FOR s` allocates a value inside the snapshot transaction; MariaDB has the same sequence syntax, so the rule closes that gap there too, while a MariaDB share with "Allow writes" keeps its sequences (Eng M3). They sit on the read-only path, not on the both-modes function denylist, and are not repeated in `TIDB_FUNCTIONS`.
- Multi-word patterns (`NEXT VALUE FOR`, and on `tidb` a user-written `AS OF TIMESTAMP`) are matched as token sequences on comment-blanked code (the matcher `escape_pair` uses), in the read-only path too, so `NEXT /**/ VALUE FOR` or a newline between the words is still refused (Eng L3).
- `TIDB_FUNCTIONS` (refused in both modes) holds the lock functions `RELEASE_LOCK`, `RELEASE_ALL_LOCKS`, `IS_USED_LOCK` and `IS_FREE_LOCK` (`GET_LOCK` and `LOAD_FILE` are already in MySQL's list), plus `TIDB_DECODE_SQL_DIGESTS` (returns other sessions' statement text, around the `CLUSTER_STATEMENTS_SUMMARY` deny), `TIDB_MVCC_INFO` (old and deleted row versions, outside the snapshot) and `TIDB_BOUNDED_STALENESS` (Eng H4).
- `TIDB_BUILTIN_VERDICTS` writes out a verdict for every TiDB 8.5.7 `SHOW BUILTINS` name matching `%LOCK%`, `%VAL`, `SLEEP`, `%FILE%` or `TIDB_%` (2026-10-18 probe). Denied: the lock functions above, `GET_LOCK`, `LOAD_FILE`, `NEXTVAL`/`SETVAL`/`LASTVAL` (read-only path), `TIDB_DECODE_SQL_DIGESTS`, `TIDB_MVCC_INFO` and `TIDB_BOUNDED_STALENESS`. Allowed (pure or local): `INTERVAL`, `SLEEP` (bounded by the 30s agent timeout, as on MySQL), `TIDB_CURRENT_TSO`, `TIDB_DECODE_BINARY_PLAN`, `TIDB_DECODE_KEY`, `TIDB_DECODE_PLAN`, `TIDB_ENCODE_INDEX_KEY`, `TIDB_ENCODE_RECORD_KEY`, `TIDB_ENCODE_SQL_DIGEST`, `TIDB_IS_DDL_OWNER`, `TIDB_PARSE_TSO`, `TIDB_PARSE_TSO_LOGICAL`, `TIDB_ROW_CHECKSUM`, `TIDB_SHARD` and `TIDB_VERSION`.
- Over MCP on `tidb`, the optimizer hints `SET_VAR`, `MEMORY_QUOTA` and `RESOURCE_GROUP` are refused (matched on the raw uppercased text inside `/*+ … */`), because they raise a read's memory quota or leave its resource group on a shared cluster (Eng L6).
- Over MCP on `tidb` (`mcp: true`; the user's own Metrics widgets are not limited), TiDB-only catalog tables are deny-unless-allowed from one complete, hard-coded set (Eng H2), not by prefix: `TIDB_ONLY_TABLES` holds the 62 `INFORMATION_SCHEMA` tables TiDB 8.5.7 has and MySQL 8.4 lacks (2026-10-18 probe: the `CLUSTER_*`, `TIKV_*`, `TIDB_HOT_*`, `INSPECTION_*` and `METRICS_*` families plus `ANALYZE_STATUS`, `ATTRIBUTES`, `CLIENT_ERRORS_SUMMARY_*`, `DDL_JOBS`, `MEMORY_USAGE*`, `PLACEMENT_POLICIES`, `RUNAWAY_WATCHES`, `SLOW_QUERY`, `TABLE_STORAGE_STATS`, `TIDB_SERVERS_INFO`, `TIDB_INDEX_USAGE`, `TIFLASH_*`, `TRX_SUMMARY` and the rest) and the 13 `PERFORMANCE_SCHEMA` pprof tables (`TIDB_PROFILE_*`, `TIKV_PROFILE_CPU`, `PD_PROFILE_*`, which run profilers and reach PD over HTTP); every `METRICS_SCHEMA` name is denied. The reviewed-allow list is written out: per-node `STATEMENTS_SUMMARY`, `STATEMENTS_SUMMARY_HISTORY`, `STATEMENTS_SUMMARY_EVICTED`, `TIDB_INDEXES`, `TIDB_TRX`, `DEADLOCKS`, `DATA_LOCK_WAITS`, and schema/session metadata `SEQUENCES`, `TIDB_CHECK_CONSTRAINTS`, `TIFLASH_REPLICA`, `SESSION_VARIABLES`, `SESSION_STATUS`, `GLOBAL_VARIABLES`, `GLOBAL_STATUS`, `VARIABLES_INFO`. The cluster-wide `CLUSTER_*` views stay denied: per-node parity with what MySQL exposes, with cluster-wide fan-out denied.
- Matching (Eng H1): names are matched as whole words on the raw uppercased text with backticks stripped (so `` information_schema.`CLUSTER_LOG` `` is caught, as the function denylist already reads raw text), and only when the statement names `INFORMATION_SCHEMA`, `PERFORMANCE_SCHEMA` or `METRICS_SCHEMA`, so a user's own `metrics_daily` or `cluster_nodes` table stays readable. A TiDB run whose connection's database is one of those three schemas is refused (`USE` is already refused, so that is the only unqualified route). Known false positive: a user table that shares a denied name, queried in the same statement as a system schema, is refused.
- `SHOW` on `tidb` over MCP is allow-listed by the words after `SHOW` (Eng H3): `[FULL] TABLES`, `[FULL] COLUMNS`/`FIELDS`, `CREATE TABLE`/`VIEW`/`DATABASE`/`SCHEMA`/`SEQUENCE`, `INDEX`/`INDEXES`/`KEYS`, `DATABASES`/`SCHEMAS`, `TABLE STATUS`, `[GLOBAL|SESSION] VARIABLES`/`STATUS`, `WARNINGS`, `ERRORS`, `COLLATION`, `CHARACTER SET`/`CHARSET`, `ENGINES`, `[FULL] PROCESSLIST` and `GRANTS`. Every other `SHOW` (`CONFIG`, `PLACEMENT`, `TABLE … REGIONS`/`NEXT_ROW_ID`, `PUMP`/`DRAINER STATUS`, `IMPORT JOBS`, `BACKUPS`, `DDL JOBS`, `STATS_*`, `SESSION_STATES` and the rest) gets the family-deny template.
- Two live tests keep this honest on the CI TiDB: `tidb_cluster_tables_are_reviewed` asserts every `INFORMATION_SCHEMA` and `PERFORMANCE_SCHEMA` table on the server is either in a hard-coded MySQL 8.4 name list or in `TIDB_ONLY_TABLES`, so a TiDB version bump that adds a table fails CI instead of opening it; `tidb_builtins_with_side_effects_are_denied` asserts every `SHOW BUILTINS` name matching the patterns has an entry in `TIDB_BUILTIN_VERDICTS`. Tested range: TiDB 8.5 (CI); ENGINES.md says so.
- `EXPLAIN ANALYZE` executes its statement. It is fine for reads, and DML is refused anyway, so no new rule; a suite row proves `EXPLAIN ANALYZE INSERT …` is refused.

### 3. Engine selection (`profiles::guard_engine`, `src-tauri/src/profiles.rs`:173)
- `base == "mysql"` with a saved or detected `tidb` gives `"tidb"` for the guard's rules (read-only, denylists), the same shape as CockroachDB.
- One engine drives both rules and wrapper. Over MCP, a connection saved as `tidb` whose server is detected as something else (a genuine MySQL or MariaDB) is refused: "This connection is saved as TiDB but the server is <product and version>. Open the connection in TableIQ, set Profile to <MariaDB or MySQL>, then share it again." The same line shows under its Settings row once a session has detected the mismatch. A session whose detection failed is already refused by `agent_block`. Widgets use the detected product's own engine (so a MariaDB saved as `tidb` keeps working widgets under MySQL's wrapper); without an open session, `validate_widget_sql` uses the saved profile's rules for its check only.

### 4. Writes always refused (`src-tauri/src/mcp/server.rs` `run_query_body` :520)
- Order in `run_query_body`: (1) `saved_engine = guard_engine(base, saved, an already-open session's detected_product() if one exists)`; `writes = entry.writes && !read_only_product(saved_engine)`; only `guard_sql(saved_engine, sql, writes)` runs here, no statements are built. (2) `session()` connects. (3) `live_engine = guard_engine(base, saved, drv.detected_product())`; recompute `writes = writes && !read_only_product(live_engine)`; guard again with `live_engine` if it differs. (4) If the saved profile is `tidb` and the detected product is not, refuse with the mismatch message. Build the statements with `live_engine` (rules and wrapper together); run; `forget_meta` only if `writes`. `read_only_product(e) = profiles::lookup(e).is_some_and(|p| p.agent_read_only)`.
- Defense in depth: `guard()` itself treats `tidb` as read-only (`writes && engine != TIDB`), so `guard_sql("tidb", sql, true)` refuses writes too; and `guarded()` uses the read-only statements (with the snapshot wrapper) for any `agent_read_only` engine even when `writes` arrives true, so no path runs TiDB SQL outside the wrapper.
- The tool description (:683-696) adds TiDB to the recognised list, adds "TiDB: reads only, from a snapshot taken when the query starts", and drops "such as TiDB are refused".
- CP3 (named refusal): in `run_query_body`, whenever the rules engine is `agent_read_only` and the guard's refusal starts with `guard::WRITE_REFUSAL` (one const that every write refusal is built from, so a rewording cannot silently drop the TiDB text; Eng L2), or the server returns `only support read-only statement during read-only staleness transactions`, the error reads "TiDB is shared read-only with agents: <original reason>. Writes to TiDB are never available over MCP, even with 'Allow writes'; ask the user to run it in TableIQ. See docs/ENGINES.md#tidb-over-mcp".
- Family-deny refusal (one template, asserted in `guard_suite`): "<name> is not available to agents on TiDB: it reads node log files, another server, or other sessions' SQL across the cluster. Use <allowed alternative> instead; the user can see the rest in TableIQ's Metrics widgets. See docs/ENGINES.md#tidb-over-mcp". Alternatives per family: `CLUSTER_STATEMENTS_SUMMARY*`/`CLUSTER_SLOW_QUERY`/`SLOW_QUERY` → `INFORMATION_SCHEMA.STATEMENTS_SUMMARY`; `CLUSTER_PROCESSLIST` → `INFORMATION_SCHEMA.PROCESSLIST`; every other denied `TIDB_ONLY_TABLES` name, every `METRICS_SCHEMA` name and every `SHOW` outside the allow list → "no agent alternative" (Metrics widgets only). A connection whose database is `information_schema`, `performance_schema` or `metrics_schema` reads: "This connection's database is <name>, which agents cannot query on TiDB; share a connection to an application database." `SET @@tidb_snapshot` and a user `AS OF TIMESTAMP` read: "TableIQ chooses the snapshot (query start); a custom read timestamp is not supported over MCP." Lock, sequence and `/*T!` refusals keep the existing function-denylist and scanner texts. Function-denylist and scanner refusals keep their own text. This holds whether or not the entry had writes ticked. Known limit: a TiDB saved as plain MySQL, with no session open yet, is refused at step 1 with the plain MySQL message (TiDB is not known until connect).
- CP4 (clock skew): `pub fn explain_tidb_error(msg: &str) -> Option<String>` in `mcp/guard.rs` maps `cannot set read timestamp to a future time` to "TiDB could not read as of now: the TiDB node's clock is ahead of its timestamp oracle (PD). This is usually clock skew; check clock sync (NTP) on the TiDB nodes." Before mapping, the MCP path and `widget_rows` retry the whole wrapped read once on exactly that error, in case TiDB's TSO view briefly lagged (Eng M2; the 2026-10-18 probe ran 2,400 concurrent snapshot reads with zero errors on single-node TiDB, so this is a cheap guard, not an observed failure). Used by the MCP `rows_of` path and by `widget_rows`.
- CP2 (`list_connections`): each entry gets `writes: "allowed" | "off" | "never" | "unverified"` (`never` for MongoDB, Redis and any `agent_read_only` product; `unverified` for a writes-ticked MySQL-based entry with no session yet, whose product is only confirmed at connect; `off` when the user did not tick writes), `read_note: Option<String>` (the profile's `agentReadNote`) and `warnings: Vec<String>` (the §7 grants warning). The `list_connections` description adds: "`writes: never` means every write is refused; `read_note` explains the engine's read semantics." The `run_query` description keeps its TiDB sentence next to the engine list. Metadata tools (`list_tables`, `describe_table`) use driver introspection, not agent SQL, so they need no wrapper on TiDB; a live assertion covers `list_tables` on a `tidb` share. It uses the saved profile, plus an open session's `detected_product()` when one exists; the tool text says a write may still be refused when the server turns out to be read-only at connect.

### 7. Privilege warning for read-only shares (CEO voice F1)
- On TiDB the guard is the only barrier against DDL, so the role's grants are checked independently (Eng M1). Where it runs: on the first agent `session()` for a TiDB connection, and when the user ticks Share while a TiDB session is open. It runs `SELECT CURRENT_ROLE()` and then `SHOW GRANTS FOR CURRENT_USER()` (with `USING <active roles>` when any are active, so privileges that come from a role are expanded). Where it lives: a per-connection-id cache in the shared app state, cleared when that connection's session closes or reconnects (so a credential change re-checks). Settings reads it through one new IPC command, `mcp_share_warnings`; before any session has run the check, Settings shows nothing for it.
- The check is an allow list, on any object scope (agent SQL can name any database): a grant line with any privilege other than `USAGE`, `SELECT`, `SHOW VIEW` or `SHOW DATABASES` is risky.
- `risky_grants` returns categories, and the warning is worded from them: reading beyond the data (`FILE`, `PROCESS`) → "This role can read server files or other sessions' SQL (<grants>)."; every other risky privilege (`ALL`, `SUPER`, `CREATE`, `CREATE VIEW`, `ALTER`, `DROP`, `INDEX`, `CREATE USER`, `GRANT OPTION`, `CONFIG`, `RELOAD`, `SHUTDOWN`, `*_ADMIN` and the rest) → "This role can change the schema or the server (<grants>)." Each ends: "Agents get read-only SQL from TableIQ's guard, but a read-only role is the safer boundary." Settings → MCP shows it under the TiDB row with a "Copy read-only role SQL" button that copies:
  ```sql
  CREATE USER 'tableiq_agent'@'%' IDENTIFIED BY '<password>';
  GRANT SELECT, SHOW VIEW ON `<shared database>`.* TO 'tableiq_agent'@'%';
  ```
  `list_connections` returns it in `warnings`. Sharing is not refused (warn, not refuse). The check runs once per session and is cached; a failing `SHOW GRANTS` gives "Could not read this role's grants (SHOW GRANTS failed: <server error>). Sharing still works; check that the role is read-only yourself."
- Pure function `risky_grants(grants: &[String]) -> Vec<String>` parses the grant lines; unit-tested on real TiDB grant text.

### 8. Alternatives considered (CEO voice F3)
- *Per-connection agent credentials* (a separate read-only user, checked by the grants probe) would make the role the boundary and could open every closed MySQL/Postgres-compatible product at once. Not chosen for this slice: it needs credential storage per share, a setup flow and a migration for existing shares, and it does not replace the guard. The grants check in §7 is its first step; TODOS T1 (generalised to every `agentReadOnly` share, with a least-privilege role helper) becomes the next P1 item before opening further products one at a time.
- *`SET SESSION tidb_snapshot` set by TableIQ*: a session variable rather than a transaction; it does not refuse DML and leaks across a pooled connection if a read fails mid-way. Rejected.
- *`TIDB_BOUNDED_STALENESS`*: stale per the 2026-10-18 probe. Rejected.
- Never enable `tidb_enable_noop_functions`.
