# Account-free onboarding and credible traction

Independent research prepared November 15, 2026 using GPT-6.1 Sol. Primary documentation and public source were checked on that date; the researcher did not install and run each application. This is a product recommendation, not customer validation, a telemetry audit or legal advice. [Current strategy](../../GTM.md) · [Blank operating scorecard](../TRACTION.md).

## Decision for TableIQ

**Release without mandatory Google sign-in or a compulsory questionnaire. Keep the current release account-free and without telemetry.** Add a voluntary feedback relationship through existing support routes; consider narrowly scoped, default-off opt-in usage measurement only as a separate later project. An email provides contactability, not evidence of activation, continued use or value.

TableIQ is an AGPL desktop database client with no required cloud/account promise and no identity backend. Introducing authentication now changes the product promise and adds a service dependency before users have demonstrated a need for one. It competes with finishing the release and demonstration videos. Any conversion harm is a hypothesis, not a percentage established by this research. No auth, analytics, collector or website implementation is authorized by this document.

The common useful pattern is a usable local product, with identity requested for services that need it. These examples do **not** prove account-free onboarding caused growth. Product size, founder audiences, licensing, distribution and maturity confound that inference. Documentation/source is stronger evidence of intended behavior than homepage positioning, but is not a network capture of a particular shipped binary.

## Week-one evidence without a login wall

Use two tracks. First, give each channel/message a campaign link and record existing landing visits where available, download-link clicks, release-asset requests and voluntary feedback submissions. Separate release versions and known upgrades. Exclude bots/repeated requests only where the data supports it, record the method and retain unknowns. Call the result **download requests**, never people or active installations. GitHub asset totals alone cannot deduplicate humans or prove launches. Campaign clicks do not automatically connect to a local installation; source attribution must remain separate unless explicitly supplied.

Second, recruit an optional beta panel through the release page, Help or existing support route. Ask optional email, intended workflow/database, discovery source and permission for planned follow-ups. Avoid required employer/name fields and keep newsletter permission separate. Approximately 10–15 willing conversations is a practical research target, not a traction claim. Store identities/consent privately outside the repository. Observations use synthetic data, not credentials or real customer rows.

At D7, ask whether the participant completed a real task, returned and encountered a blocker. At D14, ask about qualifying repeat tasks during days 8–14 and reasons for choosing the old tool. Schedule from each first launch, not the announcement date. Nonresponses are unknown outcomes, not confirmed churn. The formal cohort in [VALIDATION.md](../VALIDATION.md) retains its day-8/day-14 contacts and predefined return criterion; a D7 panel check-in is optional early feedback. Week one cannot yield D14 retention.

A truthful initial report states requests, voluntary panel size, observed task outcomes, method and known blockers. It does not claim population retention. The earlier acquisition plan needed a clearer feedback loop; publishing and counting stars/downloads alone cannot establish recurring value. A login wall would improve contactability while leaving that evidentiary gap.

## Optional measurement later

If manual follow-ups leave a material decision unanswered, scope explicit opt-in pseudonymous install measurement separately. Default off; equally easy skip; published event list; generate the random ID only after consent. Candidates are first consented launch, first successful connection, first predefined meaningful task and at most one active-use event per day. Send only version, OS/architecture, event enum and coarse time. Exclude SQL, results, credentials, hosts, paths, database/table names and raw errors. Publish retention/deletion controls and disclose network metadata before implementing the collector.

A persistent random ID is pseudonymous, not a verified person or guaranteed anonymity. Devices, reinstalls, offline activity and resets complicate counting. Measure activation against all eligible consented starts, not just successful users; define launch versus meaningful-task return. Publish mature D7/D14 numerators/denominators and selection bias. Never extrapolate opt-in retention to all downloaders or silently connect IDs to feedback email.

## When accounts become appropriate

Shared workspaces, hosted sync, billing, paid AI quotas and organization permissions create concrete identity requirements. Request sign-in at those service boundaries, with providers selected from customer needs rather than Google-only convenience. A protected allowlisted beta can also justify access control if that is an explicit product decision. TableIQ's current public local preview has no such requirement. “We need details to show traction” is not sufficient reason to gate it. Implementing auth/analytics now would expand the release scope without establishing repeat value.
